# Make Story the Reader aggregate root

Story ordering remains stable when membership grows: adding a newer Entry does not move an already-read Story to the top. Until Pulse introduces an explicit new-coverage concept, Story lists use the representative Entry (or initial Story formation time) as the stable time key.

Pulse will make Story the aggregate root for Reader state, user organization, and Reader counts so those behaviours have one owner. Aggregated Reader lists return Stories, while Source browsing continues to show Source Entries with reader state projected from their owning Story; all Reader counts, including Source-filtered counts, count distinct Stories. Acquisition diagnostics remain Candidate- and Entry-based because they measure source ingestion rather than Reader objects. The Story table does not persist derived member counts or first/last publication timestamps; queries compute them from Story membership and Entries, accepting the read cost to eliminate projection drift until measured scale justifies a new projection. The backend computes exact distinct-Story Reader counts for global, Source-filtered, and state-filtered queries; clients never infer them from loaded pages or sums of Source badges. Story and Source Entry lists use cursor pagination with exact totals rather than the pre-release offset contract. Story-list page totals count Stories, while Source Entry-list page totals count Entry rows and are named separately from distinct-Story Reader statistics.

User-maintained display titles, Notes, and tags belong to Story; a Story display title is primary in every Reader context, while Source browsing also shows the Entry source title as provenance, while source titles, content, provenance, and clustering inputs remain on Entry. A newly joined Entry inherits its existing Story reader state without making a read Story unread, and merging Stories preserves reader actions already present on either side. During migration, reader state and tags from member Entries are unioned into their Story. A single distinct non-empty user title or Note is moved to Story; multiple different non-empty values fail the migration preflight and are reported for explicit resolution instead of being overwritten. View migration and user-facing View work are deferred from this change. Rules continue to evaluate Entries, but Reader actions produced by a matching rule apply to the owning Story; Entry-scoped actions require separate explicit semantics. Notification and Webhook Effects remain Entry-scoped ingestion effects and are not deduplicated by Story in this change. Aggregated search evaluates every member Entry, returns each matching Story once, and identifies the matching Entry as result context; Source-scoped search continues to list Source Entries. PostgreSQL enforces at transaction commit that every Entry belongs to exactly one Story; application ordering alone is not considered sufficient. At commit every Story is non-empty, has a non-null representative Entry that is one of its members, and merge operations remove emptied Stories in the same transaction while recording aliases from removed Story IDs to the surviving canonical Story, so old references continue to resolve. A Story representative remains stable as membership grows; it changes only when explicitly selected or when the current representative leaves, after which the earliest-joined remaining Entry is selected deterministically. This change includes an explicit set-as-default-source action; merely switching the viewed Entry does not persist a representative change. Manual Story merge and Entry split remain available to correct clustering decisions without merging or deleting Entry content. Automatic clustering may only absorb the single-Entry Story created for a newly ingested Entry into an existing Story; it never merges two established multi-Entry Stories. If either side has conflicting user-maintained title or Note metadata, the merge requires the manual conflict-resolution flow. A manual merge unions reader state and tags, but conflicting user titles or Notes require explicit user resolution rather than silent overwrite. A Story created by splitting out an Entry inherits the original Story reader state so correcting membership does not undo prior user actions. User titles, Notes, and tags remain on the original Story by default; when such metadata exists, the split flow lets the user explicitly copy or move selected metadata to the new Story. Story is the sole persistence owner of read, starred, hidden, and later state; these columns and state mutations are removed from Entry, including the old Entry reader-state HTTP contract; the pre-release API makes a clean break without a compatibility forwarding layer, and Source Entry queries join the owning Story instead of maintaining synchronized copies. When a Source has multiple Entries in one Story, Source browsing retains each Entry row but visibly relates the rows, shares the Story reader state, and counts the Story once for Reader statistics. Source content browsing is exposed as `/sources/{sourceId}/entries`, while aggregate Reader browsing is exposed only through Stories; there is no optional-Source generic Entry Reader list. Their interface returns an explicit composite of Entry content and a real Story identity plus reader state, rather than flattening projected state onto Entry or inventing synthetic Story IDs. Source-scoped bulk reader actions first select distinct Stories containing Source Entries and then update those Stories, so related Entries in other Sources reflect the same result. Reader removal hides a Story reversibly; permanent Entry deletion remains an explicit source-data maintenance action and creates the existing Entry Tombstone. Deleting the final Entry requires explicit confirmation that the non-empty Story and its user metadata will also be deleted; an empty Story is never retained.
